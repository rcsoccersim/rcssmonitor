## 1. Goal and scope

Before the official release of rcssmonitor 20.0.0, the following features are added (the version is already 20.0.0-beta.1, but it has not been released. `docs/dev/release.md` §0).

| # | Feature | Kind | Plan |
|---|---|---|---|
| F1 | Choose the color scheme (light/dark), as soccerwindow2 does | Required | This document, §A |
| F2 | Keep the icons as PNG instead of XPM (the same way as soccerwindow2) | Required | [2026-11-22-01_icon-redesign_en.md](2026-11-22-01_icon-redesign_en.md) |
| F3 | Find and start it from the GNOME desktop search | Required | This document, §B |
| F4 | Blow the referee's whistle when the play mode changes | Nice to have | This document, §C |
| F5 | Download an rcg from a given URL and play it. Lists of the logs on GitHub and the archive | Nice to have | [2026-11-22-02_remote-logs_en.md](2026-11-22-02_remote-logs_en.md) |
| F6 | Export what is drawn on the screen as an image sequence or a video | Nice to have | [2026-11-22-03_frame-export_en.md](2026-11-22-03_frame-export_en.md) |

- The plans are split by the size of the features. The three small ones (F1, F3, F4) are in this document, and the three large ones (F2, F5, F6) have their own plans.
- This document also has the overall order and branches, the decisions shared by the features, and the way to the release.

| S4 | Avoid adding tabs to the config dialog. If one is added, also fix the tab lists in `test_config_dialog.cpp` (lines 287, 417) | The tests pin the tab list |

## §A Color scheme (light/dark)

### A.1 Current state (develop 5affd90)

- There is no way to choose the color scheme. View > Window Style only chooses the Qt style (QStyle).
- The chosen style is not saved: `MainWindow::changeStyle()` (main_window.cpp:2436) does not update `M_window_style`. Its default `"plastique"` does not exist in Qt5/Qt6, so `QApplication::setStyle( M_window_style )` at startup (line 167) fails and the platform style stays.
- The toolbar icons are XPMs or shapes drawn by code, recolored with `QPalette::ButtonText` (`tintIcon` in `src/tool_icon.cpp`, `src/toolbar_icons.cpp`). When the palette changes, `MainWindow::updateToolIcons()` (line 1470) recolors them.
- The drawing of the field (2D and 3D) does not depend on QPalette. The colors are the `Options` settings (the Color tab) or colors written in the code.
- What depends on the palette: the background of the view stack (`M_view_stack`) is set to black (line 1103; `test_view_switch.cpp` checks it), the red of an error in the cycle field (lines 1588-1599), the red of an out-of-range number in the config dialog (`markNumber`, config_dialog.cpp:1731), the color of an error in the figure pack credits (`color: #c03030;`, line 2725), and the tooltip marker (`tooltip_marker.cpp`, `WindowText`).

### A.2 Approach (port soccerwindow2's implementation)

Same as soccerwindow2 (`../../rctools/soccerwindow2`; commits 7e87a9c, 8a15c38; Phase 5 of its plan `docs/plan/2026-11-19_qt6-cmake-migration.md`).

- `src/ui_palette.{h,cpp}` (new): `UIPalette::light()` and `UIPalette::dark()`, built by hand with the same colors as the Fusion palette of Qt 6.5 or later (`qt_fusionPalette()`). They look the same with Qt5 and Qt6. From `soccerwindow2/src/qt/ui_palette.cpp`.
- `src/ui_style.{h,cpp}` (new): a `QProxyStyle` that draws the checked toolbar buttons as a translucent rounded rectangle of the highlight color, because the checked state is hard to see in the dark scheme. From `soccerwindow2/src/qt/ui_style.cpp`.
- `Options`: `ui_color_scheme` = `system` | `light` | `dark` (default `system`). Command line `--ui-color-scheme {system,light,dark}`. Saved only when chosen from the menu; a value given on the command line is not saved (same as soccerwindow2). It is written to `ui_color_scheme` of `[MainWindow]` at once when chosen from the menu (U7; `Options::writeUIColorScheme()`). `Options::writeSettings` writes the default only when it makes the settings file (`all`).
- Menu: View > UI Color Scheme > System / Light / Dark. An exclusive `QActionGroup`, next to Window Style.
- Applying: `QApplication::setPalette()`. System is the `QApplication::palette()` taken when MainWindow is created (so that tests can fake a dark desktop). After the Qt style is changed, the scheme is applied again (because `setStyle` resets the palette).
- To review in the dark scheme: what depends on the palette in A.1, the player type dialog, the list of the Color tab of the config dialog. The colors of the field (2D and 3D) and the 3D HUD are not changed (same as soccerwindow2).
- To check: with Qt 6.5 or later and System chosen, whether it follows a change of the desktop's scheme while running. If not, decide with the user how far to support it. → Cannot be checked in this environment (Qt 6.4.2) (A.6).
- The window style not being saved (A.1) is fixed too (U8): the default is empty (the platform's), the style chosen from the menu goes into `M_window_style`, and it is saved when the window closes (`MainWindow::writeSettings`). When no style has the saved name (e.g. `plastique`, written by older versions), the platform's style is used and the name is cleared.

### A.6 Implementation (2026-11-22)

- `src/ui_palette.{h,cpp}` (new): the enum of the schemes `UIColorScheme` (System, Light, Dark) and the conversion of the names (in the same form as `GrassMode` etc. of `camera_mode.h`). `UIPalette::light()`, `dark()` (the same colors as soccerwindow2), `of( scheme, system )`, `isDark( palette )` (the icons (F2) use it too), the error colors `errorText()` and `errorBase()`, and the error marks `markWrongField()`, `markWrongText()` and `updateWrongMarks()`.
- `src/ui_style.{h,cpp}` (new): soccerwindow2's `UIStyle`. Changed from the plan: the condition of the emphasized buttons was widened from "the parent is a tool bar" to "an ancestor (in the same window) is a tool bar". rcssmonitor's buttons are laid out in a QFrame in the tool bar, and soccerwindow2's condition did not emphasize them (found from offscreen images).
- `Options`: `ui_color_scheme` (U7), `--ui-color-scheme`, `writeUIColorScheme()`.
- `MainWindow`: View > UI Color Scheme (System, Light, Dark; below Window Style), `applyUIColorScheme()` (called by `init()`, the menu, and after a style change), saving the window style (U8). `init()` wraps the saved style (or the current one if none) with `UIStyle`.
- The review in the dark scheme (each place of A.1):
  - The cycle field and the number fields of the config dialog (`markNumber`): when the error color was removed, `setPalette( QApplication::palette( w ) )` fixed all the colors of that time, so they stayed in the previous colors after a scheme change. The config dialog calls it for all its number fields whenever it updates its display, so all of them stayed. With `UIPalette::markWrongField()`, only the Base color is set on an error, and nothing otherwise. Fields with an error are marked again in the new scheme's colors by `MainWindow::changeEvent` (`updateWrongMarks`) when the scheme changes.
  - The error color of the figure pack credits: the style sheet `#c03030` (2.3:1 on the dark background) was replaced by a red that follows the scheme via `markWrongText()` (#c03030, 4.9:1, in the light scheme; #ff7070, 4.8:1, in the dark one).
  - The color swatches of the Color tab of the config dialog: white melted into the light background and black into the dark one, so a gray (128, 128, 128) border was added.
  - The black background of the view stack (only `Window` is set, so it follows the scheme), the tooltip markers, the player type dialog, and the other tabs of the config dialog were fine as they were (checked with images written offscreen).
- Found:
  - With Qt6 (6.4.2), the palette of `QApplication::setPalette()` reaches the widgets when the events are processed (Qt5: at once). The real application is in the event loop, so this is no problem. The tests process the events after choosing.
  - Qt's `-style` option takes effect only when no style is saved (the saved style wins). A style chosen by `-style` is not saved.
  - Following the desktop while running with Qt 6.5 or later (A.2) cannot be checked in this environment (Qt 6.4.2). The palette set for System is the one taken when MainWindow is made (not yet set by the application itself), which Qt6 completes with the theme's palette of the time, so it is expected to follow. Check it when an environment with Qt 6.5 or later is at hand.

## §B Desktop (find and start it from GNOME)

### B.1 Current state (develop 5affd90)

- The default installation prefix of CMake is `~/.local` (PR #69). From `data/rcssmonitor.desktop.in`, a desktop entry with the absolute path of the installed `bin` in `TryExec` and `Exec` is made and installed in `share/applications` (CMakeLists.txt:148-166). Only the 48×48 `icons/rcssmonitor.png` is installed as the application icon, in `share/icons/hicolor/48x48/apps` (line 167).
- The user's environment has `~/.local/share/applications/rcssmonitor.desktop` and the 48×48 icon installed.
- The desktop entry has no `GenericName`, `Keywords` or `StartupWMClass`. It is not found by "robocup" or "soccer". `Categories=Development;`.
- `QGuiApplication::setDesktopFileName()` is not called (`src/main.cpp` only calls `setApplicationName` and `setApplicationVersion`). There is no guarantee that the Wayland app_id is tied to the desktop entry, so the icon in the dash and the grouping of the windows may be wrong.
- The window icon is the 48×48 XPM (`main_window.cpp:105`).
- Autotools installs neither the desktop entry nor the icon (`docs/build.md`).
- `cmake/DistCheck.cmake` checks the installed desktop entry (`TryExec`/`Exec`, `desktop-file-validate`) and the 48×48 icon.

### B.2 Approach (follow soccerwindow2's desktop-entry plan)

Follow soccerwindow2's `docs/plan/2026-11-21_desktop-entry.md` (commits e8478dc, d5e34d3, 1cead0d, d8dce5f).

- `src/main.cpp`: `QGuiApplication::setDesktopFileName( QStringLiteral( "rcssmonitor" ) )`. The Wayland app_id becomes the name of the desktop entry, and GNOME's dash shows the right icon. On X11 they are tied by `WM_CLASS` and `StartupWMClass`.
- The window icon is the application icon in all sizes made by the icon plan (F2) (`UIIcon::appIcon()`).
- Add to `data/rcssmonitor.desktop.in`: `GenericName=RoboCup Soccer Simulator Monitor`, `Keywords=RoboCup;soccer;simulator;monitor;logplayer;`, `StartupWMClass=rcssmonitor`.
- Installation: install the application icon in hicolor 16, 32, 48, 64, 128, 256 and scalable (SVG) (CMake and autotools).
- Autotools also installs the desktop entry, with a rule that replaces `@RCSSMONITOR_BINDIR@` by `$(bindir)` with `sed`. Check whether an autotools build finds `librcssrcg` without `LD_LIBRARY_PATH` (the RPATH of libtool). → It did not (B.5).
- `cmake/DistCheck.cmake`: update the checks of the icon sizes and the desktop entry.
- `test/check_desktop_entry.sh` (new): validate the template with `desktop-file-validate` (skip with exit code 77 if it is missing). Register it in CTest.
- Documents: the table of installed files in `docs/build.md`, and the description of the desktop entry in README.
- To decide with the user at the start of the stage:
  - `Categories`: keep `Development;`, or follow soccerwindow2's `Science;ArtificialIntelligence;`.
  - Whether to add "Connect to the server" to the right-click menu (`Actions=connect;`, `[Desktop Action connect]` running `rcssmonitor --connect`). soccerwindow2 added it.
  - Whether to associate `.rcg` files (`MimeType`). soccerwindow2 did not.
  - Whether to add translations (`Name[ja]` etc.). soccerwindow2 did not.
  - → Decided by the user (2026-11-23): U9 (`Science;ArtificialIntelligence;`) and U10 (add "Connect to the Server"; no `MimeType` and no Japanese translation).

## §C Referee's whistle

### C.1 Current state, and where to catch the moment to blow it

- There is nothing that plays sounds. Qt Multimedia is not used anywhere, and the build does not look for it. This environment (Ubuntu 24.04, Qt 6.4.2) does not have `qt6-multimedia-dev` installed (the package exists).
- When the shown frame changes, `LogPlayer::indexUpdated(current, max)` is emitted (log_player.cpp): on timer playback, stepping, moves by the slider or jumps, live (`showLive`, line 444), delayed live (`showDelayedLive`, line 578), and the move to the first frame when a log is opened.
- The play mode of frame i is `DispHolder::dispCont()[i]->pmode_` (`rcss::rcg::PlayMode`, `rcss/rcg/types.h:60`). `DispHolder::playmode()` is the last mode read, not the shown one.
- Where the index moves without a signal: `LogPlayer::setLiveMode()` (line 478), `DispHolder::trimLiveFrames()` (disp_holder.cpp:261; drops old frames and shifts the indices), and `clear()`.
- Connecting to `DispHolder::handlePlayMode` is wrong: it is also called while reading a whole log, and in live mode at the time of receipt, not of display.

### C.2 When to blow it

- Connect to `LogPlayer::indexUpdated` and compare the play mode of the shown frame with the mode seen before.
- Log playback: blow it only when it advanced by one (`current == prev + 1`; timer playback and stepping forward). On jumps, the slider, stepping back and going to the first frame, do not blow it; only update the remembered mode.
- Live and delayed live: one update may advance several frames, so look at the frames in (prev, current], and if there is a transition, blow it once (the strongest whistle if there are several).
- When a log is opened (around `M_disp_holder.clear()` at main_window.cpp:1861), on connecting (line 1983), and after `setLiveMode()` and `trimLiveFrames()`, forget the remembered mode (or remember it by cycle instead of index).
- So that whistles do not overlap in fast playback, stop the whistle being played before playing the next one.
- In live mode, the 3D view draws up to 2 cycles late (`LiveClock`). The whistle may sound a little before the 3D view shows the moment; this is accepted and recorded.

### C.3 Play modes and whistles (proposal; decided with the user at the start of the stage)

#### C.3.1 The whistle in real football (the guidelines of the Laws of the Game)

The Whistle part of IFAB's "Practical guidelines for match officials" in the Laws of the Game (https://theifab.com/laws/latest/guidelines/body-language-communication-and-whistle , checked on 2026-11-22):

| The whistle is needed | The whistle is not needed |
|---|---|
| To start play (first and second half of normal play and extra time), after a goal (the kick-off) | To stop play for a clear goal kick, corner kick, throw-in or goal |
| To stop play: for a free kick or penalty kick, if the match is suspended or abandoned, at the end of each half | To restart play from most free kicks, and a goal kick, corner kick, throw-in or dropped ball |
| To restart play for free kicks when the appropriate distance (9.15 m) is required, and penalty kicks | |
| To restart play after it has been stopped for a caution or sending-off, injury, or substitution | |

- It also says that a whistle used too frequently or unnecessarily will have less impact when it is needed.
- The number of whistles at the end of each half is not in the Laws (a custom).

#### C.3.2 What rcssserver does (`../rcssserver/src/referee.cpp`)

- On fouls (`foul_*`), offsides, back passes, free kick faults, catch faults and illegal defense, it stays in that play mode for 30 cycles (3 seconds; `AFTER_FOUL_WAIT`, `AFTER_OFFSIDE_WAIT`, etc.), moves the defending players away from the ball in the last 5 cycles (`CLEAR_PLAYER_TIME`, `clearPlayersFromBall`), and then changes to `free_kick_*` or `indirect_free_kick_*`.
- So after a foul there are two clear points: "stop" (the foul mode) and "restart after making the players keep the distance" (the free kick mode). They correspond to "stop play for a free kick" and "restart play for free kicks when the appropriate distance is required" of the guidelines (both need the whistle).
- Throw-ins, corner kicks, goal kicks, etc. change directly from `play_on` to their mode, and the players are moved away from the ball when the mode changes (`FreeKickRef::playModeChange`). There are no separate points of stopping and restarting.
- `free_kick_*` after the goalkeeper's catch also changes directly from `play_on` (a scene with neither a stopping nor a restarting whistle).
- A dropped ball is `drop_ball` followed at once by `play_on` (`Referee::awardDropBall`; except in the penalty shootout).

#### C.3.3 Proposal (2026-11-22; decided in C.3.4 on 2026-11-23)

On free kicks after fouls, a short whistle for the restart is blown (two whistles with the one at the foul). As in C.3.2, the server restarts after making the players keep the distance, so this matches the guidelines of real football. The previous mode tells them apart from free kicks after a catch.

| Transition | Whistle | The guidelines |
|---|---|---|
| → `kick_off_l/r` | Short | Start, after a goal (needed) |
| → `foul_charge_l/r`, `foul_push_l/r`, `foul_multiple_attack_l/r`, `foul_ballout_l/r`, `offside_l/r`, `back_pass_l/r`, `free_kick_fault_l/r`, `catch_fault_l/r`, `illegal_defense_l/r` | Short | Stop for a free kick (needed) |
| A mode of the row above → `free_kick_l/r`, `indirect_free_kick_l/r` | Short (restart) | Restart of a free kick with the distance required (needed) |
| → `penalty_ready_l/r` (the signal that the penalty kick may be taken) | Short | Restart for a penalty kick (needed) |
| → `goal_l/r` | Long (for effect) | Not needed for a clear goal. Whether to blow it is decided at the start of the stage |
| → `first_half_over` | Long, twice | End of a half (needed; the number is a custom) |
| → `time_over` | Long, three times (end of the game) | Same as above |
| `play_on` → `free_kick_l/r` (after a catch), → `kick_in_l/r`, `corner_kick_l/r`, `goal_kick_l/r`, `drop_ball`, `play_on`, `before_kick_off`, `pause`, `human_judge`, `penalty_kick_l/r`, `penalty_setup_l/r`, `penalty_taken_l/r`, `penalty_miss_l/r`, `penalty_score_l/r` | None | Not needed to stop or restart |

- Changed from the previous proposal: a short whistle was added for the restart of free kicks after fouls. `drop_ball` gets no whistle (no whistle is needed to restart from a dropped ball; in rcssserver the ball is dropped without stopping, e.g. when a set play is not taken in time).
- Whether to blow the goal whistle, and whether the restart whistles can be turned off in the settings, are decided at the start of the stage.
- The order of the transitions in extra time and the penalty shootout is checked in rcssserver at the start of the stage. → C.3.4.

### C.9 The implementation of stage 2 (2026-11-23)

C.2 and C.4 were implemented as follows. What was decided beyond the plan is written too.

- `src/whistle.{h,cpp}` (new):
  - `WhistleSound`: the interface of the sound output (`play( long_whistle, volume )`, `stop()`, `hold( on )`). With Qt Multimedia, `StreamWhistle` plays the whistles on one audio output (`QAudioSink` of Qt6, `QAudioOutput` of Qt5; the default device; mono, 16 bits, 44.1 kHz), kept open. The output keeps reading the samples from a `WhistleMixer` (a `QIODevice`; the pull mode). `WhistleMixer` gives silence while no whistle plays, and a whistle from its start, at its volume, when `play()` is called; it never runs out of data. No output is opened or closed for a whistle. The whistles are read from the WAVs of the resources (`qrc:/sounds/...`, `Q_INIT_RESOURCE( sounds )`) by `WhistleMixer::readWav()` (only PCM, mono, 44.1 kHz, 16 bits). `WhistleMixer` is opened with `QIODevice::Unbuffered` (the buffer of `QIODevice` read about 16 KB (about 0.19 s) of silence ahead, and delayed a whistle as much). The volume (0 to 100) is the loudness heard, converted by `QAudio::convertVolume` (logarithmic to linear), as Qt recommends for a volume slider, and `WhistleMixer` scales the samples by it. When there is no default device (e.g. Qt5 without the audio plugins of Qt Multimedia, `libqt5multimedia5-plugins`), no output is made, and a warning is printed once.
  - `Whistle`: connected to `LogPlayer::indexUpdated`, it keeps the frame shown before by its pointer (`DispConstPtr`), not by its index. It stays right when `trimLiveFrames()` moves the indexes, and when a new log or a connection makes other frames (C.2's "forget the remembered mode" is done by not finding the pointer). Opening a log and connecting also stop the whistle by `clear()`.
  - When to blow it: in log replay, only when the frame shown before is the one just before. Live (`LogPlayer::isLiveMode()`), the frame shown before is looked for back up to `MAX_LIVE_STEP` (20 frames, about 2 s), and the strongest whistle of the changes in between is blown once. Going on by more is a jump (e.g. turning off the delay of the delayed live view): no whistle. Nor when the loop playback goes from the last frame back to the first.
  - The frame shown is kept while the whistle is off too, and the first change after it is turned on blows.
  - The long whistle twice and three times is repeated by a `QTimer` every `LONG_REPEAT_INTERVAL` (1300 ms: the long whistle of 0.95 s and a pause of 0.35 s). The next whistle and `stop()` also stop the repeats left.
  - In log replay, going on from the first frame also blows its kick-off if the first frame is one (U17). Not live: the first frame there is not always the start of the game.
  - The sound output is made when it is first needed (a frame shown while the whistle is on, or a whistle blown). With the default (off), the Qt Multimedia devices are not touched. When on, the WAVs are loaded at the first frame, in time for the first change.
  - Keeping the output open (`WhistleSound::hold()`, `Whistle::updateHold()`): while the whistle is on, the output is kept open (silence between the whistles), and it is closed when the whistle is turned off. PipeWire (WirePlumber) suspends an output that has played nothing for 5 s, and an HDMI output (a display's speakers) that wakes up from it loses a second or more of the start of the next sound. So the whistles after a quiet time (the short whistle that stops for a foul, the first of the three long whistles at the end of the game) were not heard. It is opened when the whistle is turned on (the menu, the config dialog), when rcssmonitor starts (`MainWindow::init()`; U19) and at a frame shown while it is on, and closed when it is turned off.
  - At the end: the output is closed by `Whistle::releaseSound()` at the start of the main window's destructor. Closing an output (destroying `QAudioSink` / `QAudioOutput`) makes Qt process events for a while (`QAudioSink` of Qt 6.4, the PulseAudio plugin of Qt5). `Whistle` is a child of the main window, so otherwise the output was destroyed while the widgets were being destroyed, and an event still to deliver reached the window being destroyed, which crashed (found by a test). Also, so that opening or closing called again by the events processed while the output is opened or closed does no harm, `StreamWhistle` marks that it is opening or closing, and a close asked meanwhile is done after the opening.
  - Why not `QSoundEffect` (found by trying it on 2026-11-23 and 24): `QSoundEffect` of Qt 6.4 (PulseAudio, on PipeWire) opens a new output for every whistle, and closes it at its end. The output starts playing only after about 0.125 s (11028 bytes) is buffered, and when the sound has been read, it is closed, dropping what is still buffered (about 0.3 s): the short whistle (0.1 s) was never heard, and the end of the long one was cut. Every output opened changed the quantum of the HDMI output between 2048 and 1024, and on the real HDMI output the second and the third of the three long whistles were cut or not heard, and no whistle nor Test was heard after them. It was once fixed by putting silence after the whistles in the WAVs, and by playing a silent WAV in a loop on another `QSoundEffect`; with the one output, both were dropped (the WAVs are the ones of stage 1 again).
- Settings (`Options`): `whistle` (default false) and `whistle_volume` (default 50, 0 to 100) in the `[Sound]` group. As the color scheme (U7, S3), they are written as soon as they are chosen in the menu or the config dialog (`writeWhistle()`, `writeWhistleVolume()`), and not at the end (the command line's values are not saved; U13's "what is chosen is saved"). The defaults are written when the settings file is made.
- Command line: `--whistle <on|off>`, `--whistle-volume <0 to 100>` (a value out of the range or not a number is reported and not used). In a build without Qt Multimedia, the help of `--whistle` says it is not available.
- View menu: "Referee's Whistle" (checkable, between separators) after 3D Camera and before Player Type List. Turning it off stops the whistle playing.
- The Show tab of the config dialog: a Sound group below Live. "Referee's whistle" (in sync with the View menu), the Volume slider (steps of 5; saved at once when changed by the keys, and when let go when dragged) with its number, and a Test button (the short whistle at that volume; enabled only while the whistle is on, when the output is kept open).
- A build without Qt Multimedia: the menu item and the Sound group are shown but disabled, with the reason ("built without the sound (Qt Multimedia)") in their tips (C.4's "disabled with the reason shown"; as the 3D View item).
- The tests' HOME: each test has a HOME of its own (`build/test/home/<name>`; `test/CMakeLists.txt`). All the tests used the settings file of the same HOME, so when run at once (`ctest -j`), a test starting removed the settings file while another one was checking a saved value, and that one failed at times (twice with Qt5's `ui_color_scheme`; more likely with the long `whistle` test, which writes the settings file).
- Tests: `test/test_whistle.cpp` (new; C.6): log replay (the whistles of the table), the play from the first frame (the kick-off of the game; none live, and none for a log that does not start with a kick-off), jumps, steps back, to the first and to the last (no whistle), the loop playback, off (no sound output made), live (one frame at a time, frames at once, a jump of more than 20), after the oldest frames are dropped, the delayed live view (blown when shown), reopening, the interval of the long whistles, stopping, the volume, the real output (with and without Qt Multimedia), the View menu, the config dialog, the command line (in a child process; not saved).
